## Findings

1. **The C++ regime flips were DVFS.** With clocks locked the three C++ repeats
   are indistinguishable (e2e mean 157.5 / 159.0 / 158.1 ms; p99 200–204 ms) and
   the mid-run flips in figL1 are gone — each run settles once, at ~7 s, and stays
   flat for the remaining 18 s. Unlocked, the same binary flipped between ~100 ms
   and ~165 ms e2e regimes mid-run.
2. **Python was never DVFS-sensitive.** Locked numbers match unlocked to 0.3 ms;
   its tail actually tightens to nearly ideal (p99 133.9 ms, max = one 163 ms
   batch per run). Its strictly periodic full-batch load keeps the system at one
   operating point with or without the lock.
3. **C++ compute is fast; the mux wait is the cost.** Locked, C++ books ~43 ms
   compute + ~115 ms held at the new mux = 158 ms, vs Python's ~100 ms compute +
   33 ms timeout = 133 ms. The new mux on file replay holds frames ≈ 3.5 frame
   periods before pushing — that pacing (see `overall-min-fps` /
   `config/mux_config.txt`), not inference speed, is the whole residual gap.
   Note the unlocked "fast regime" (e2e ~100 ms) shows the low-wait alignment
   exists; locked runs consistently settle in the high-wait one.
4. **Tail verdict flips with the lock.** Unlocked, C++ p99 (269 ms) looked 65%
   worse than Python; locked it is 202 vs 134 ms — still worse, but the honest
   number. Never compare C++ runs without locking clocks first.
5. Throughput/detection story unchanged: C++ +3.7% frames/s, +3% detections,
   fullness 3.98 vs 4.00.

  ./cpp/multicam_rt --config config/camera_params.yaml --source file --log none \
      --metrics-csv $OUT/cpp_baseline_r$i.csv --duration 25

      --metrics-csv $OUT/py_baseline_r$i.csv --duration 25
