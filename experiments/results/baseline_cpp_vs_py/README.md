# Baseline A/B — C++ (new nvstreammux) vs Python (legacy mux) on replay clips

**2026-07-07.** 3 repeats × 25 s per app, sequential, on `experiments/clips/cam0..3.mp4`
(4× 640×480@30 recorded C920 clips), YOLO11n FP16 batch-4, warmup 4 s dropped,
clocks NOT locked (no `jetson_clocks`). Both apps: `--source file --log none`,
default config (`sync-inputs=0`, fixed 33 ms timeout, all cameras active).

Figures in [`plots/`](plots/), regenerated by `python3 make_plots.py`
(reads the 6 CSVs here, writes PNGs + `summary.json`).
Exact commands + effective pipeline config: [`../BASELINE_COMMANDS.md`](../BASELINE_COMMANDS.md).

## Headline (pooled over 3 repeats)

|  | C++ (new mux) | Python (legacy mux) |
|---|---|---|
| e2e mean / p50 (ms) | 144 / 148 | **134 / 133** |
| e2e p99 / max (ms) | 269 / 347 | **163 / 249** |
| e2e p1 (ms) | **38** | 131 |
| batches/s · frames/s | **32.5 · 125.3** | 30.1 · 120.2 |
| frames/batch | 3.86 | 4.00 |
| detections / 25 s | 2533 | 2453 |
| new track IDs / run | 21–24 | 21–22 |

## Findings

1. **Python is the stability reference.** Every repeat: e2e 133 ± 0.1 ms,
   wait pinned at ~33.5 ms (= `batched-push-timeout`), compute flat ~100 ms.
   The legacy-mux contract (wait for all 4 pads or timeout) makes every batch
   identical on synchronized replay input.
2. **C++ trades steadiness for throughput.** ~8 % more batches/s by pushing
   slightly partial batches (fullness 3.86); lower latency floor (p1 38 ms) but a
   worse tail (p99 269 vs 163 ms) and a wider spread.
3. **C++ wait/compute split is attribution, not lost time.** Per repeat, wait
   ranges 12–101 ms and compute 53–145 ms while their sum stays 119–157 ms
   (fig4). `compute_ms` is mux→tracker, so queueing after the mux books as
   "compute"; held-at-mux time books as "wait".
4. **C++ flips between latency regimes mid-run** (fig3): rolling-median compute
   alternates between ~30 ms and ~130–200 ms stretches; e2e between ~100 and
   ~165 ms. Candidates: new-mux deadline batching × replay pacing, and Jetson
   DVFS (clocks unlocked). **Next:** re-run with `jetson_clocks` to separate.
   Done — [`../baseline_cpp_vs_py_locked/`](../baseline_cpp_vs_py_locked/README.md)
   confirmed the flips were DVFS, and
   [`../param_sweep_locked/`](../param_sweep_locked/README.md) showed the
   residual gap was the mux INI (`overall-min-fps=30`); with min-fps=120 the
   C++ app hits 28 ms p50.
5. **Outputs agree** — per-camera mean detections differ ≤ 0.07/batch (fig6),
   track churn identical (fig7). Same engine, same scene → the A/B is valid.

## Caveats

Replay adds H.264 decode vs live MJPG capture — absolute numbers differ from
live; relative A/B is the valid read. Accuracy column is the track-stability
proxy, not mAP.

## Reproduce

```bash
OUT=experiments/results/baseline_cpp_vs_py
for i in 1 2 3; do
  ./cpp/multicam_rt --config config/camera_params.yaml --source file --log none \
      --metrics-csv $OUT/cpp_baseline_r$i.csv --duration 25
  python3 main.py --config config/camera_params.yaml --source file --log none \
      --metrics-csv $OUT/py_baseline_r$i.csv --duration 25
done
python3 scripts/analyze.py $OUT/cpp_baseline_r*.csv $OUT/py_baseline_r*.csv --warmup 4
python3 $OUT/make_plots.py
```
